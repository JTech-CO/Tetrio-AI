# TURBO 구현·검증 요약

2026-09-21 · Windows / Node.js 25.9.0 / TETR.IO Desktop 10.0.0 · 뷰포트 1295×999, DPR 2.

## 최종 결과

**500피스 / 93.940초 = 5.323 PPS로 합격.** 의심 피스·재동기화·입력 오류·폴백 모두 0회.
[실측 JSON](turbo-validation-500-final-2026-09-21.json). 자동 테스트는 70개 통과했다.

연결·초기 보정·준비 주행 60피스는 측정에서 제외하고, 실행 중 검증·복구·키 해제 시간은 포함했다.
합격 조건은 500피스 이상, 의심 피스를 제외한 PPS ≥5, 의심 피스 ≤3%, 강제 재동기화 ≤1%, 입력 오류·폴백 0회다.

**한계:** 최종 구간에는 레벨 전환이 없었다. 1,000피스 완주는 이후 확인됐다(아래 2026-09-24·09-23 재검증).
이전 버전의 장기 성공 이후에도 전환·캡처 지연으로 실패한 시도가 있었다. 다른 환경에서 같은 속도나 무오배치를 보장하지 않는다.
의심 피스는 불일치 검증 구간 전체의 피스 수이며, 실제 오배치 수와 같지 않다.

## 2026-09-24 재검증 (1,000피스 · 창 크기별 보정)

**1,000피스 / 185초 완주, 실효 5.71 PPS.** 의심 피스·강제 재동기화·오배치·RAPID 폴백 모두 0회.
[실행 로그](turbo-run-1000-2026-09-24.txt). 측정 방식과 판정 범위는 아래 2026-09-23 기록과 같다
(`src/run.js`가 보고하는 `turboStats.effectivePps`이며, `validate_turbo.js`의 합격 판정은 거치지 않았다).

실효 PPS는 100피스 4.68 → 500피스 5.58 → 1,000피스 5.71로 끝까지 한 번도 떨어지지 않았다. 초반 값이 낮은 것은
화면 효과 고정·필드 보정·첫 판독 같은 준비 시간이 누적 평균에 포함되기 때문이며, 최근 PPS는 처음부터 5.6~6.0
구간이었다. 검증 지연은 최대 81ms였다.

**창 크기별 보정이 차이를 만들었다.** TURBO는 입력 프로필과 뷰포트가 정확히 같아야 하는데, 앱의 창 크기는 켜는
방식에 따라 달랐다 — 꺼진 상태에서 새로 실행하면 최대화(1920×1010), 최대화를 해제하면 1278×1002, 봇이 실행 중인
창 모드 앱을 재시작하면 1295×999. 보정 파일이 하나뿐이어서 한 크기를 보정하면 다른 크기의 프로필이 지워졌고,
보정 도구가 측정 전에 파일을 무효화했기 때문에 실패한 보정도 기존 프로필을 없앴다. 그 결과 TURBO가
`TURBO viewport changed`로 매번 RAPID로 떨어졌다. 이제 프로필은 `probe/turbo-calibration-<w>x<h>@<dpr>.json`으로
크기별로 저장되고, 실행 중인 크기의 프로필을 쓴다. 이 런 당시에는 맞는 프로필이 없으면 RAPID로 진행했으나,
같은 날 자동 보정으로 바뀌었다(아래 "2026-09-24 자동 보정").

| 창 크기 | 보정 결과 | 1,000피스 |
|---|---|---|
| 1278×1002 | 스폰 120·95·80·65ms 모두 통과 → **65ms** + 회전·첫 이동 동시 입력 | **5.71 PPS** (09-24) |
| 1295×999 | 95ms가 42번째 피스에서 탈락 → 120ms + 동시 입력 | 5.03 PPS (09-23) |
| 1920×1010 (최대화) | 120ms도 64번째 피스에서 탈락 → 프로필 없음 | TURBO 불가, RAPID로 진행 |

1278×1002와 1295×999의 프로필 차이(65ms / 120ms)는 창 크기보다 측정 편차일 가능성이 크다. 크기가 거의 같고,
같은 1295×999에서도 2026-09-21에는 65ms가 통과했다. 반면 최대화 창은 구조적으로 불리하다. 보정 중 검증 지연이
최대 269ms로 창 모드 보정(58~120ms)의 2~4배였고, 라인 클리어 뒤 250ms가 지나도 갱신되지 않은 프레임이
관측됐다. **TURBO는 창 모드로 실행하는 것을 권장한다.**

**한계:** 이번에도 스테이지업이 0이라 레벨 전환은 검증되지 않았다.

## 2026-09-24 자동 보정

**TURBO는 처음 보는 창 크기에서 스스로 보정한다.** TURBO가 시작될 때(플레이 중 콘솔에서 `3`으로 전환할 때 포함)
현재 창 크기의 프로필이 없으면 그 자리에서 입력 보정을 돌려 저장하고 곧바로 TURBO로 플레이한다. 보정 시간과
보정 중 놓은 피스는 실효 PPS와 실행 통계에서 뺀다. 수동 보정(`npm run turbo:calibrate`)도 같은 코드
([autocalibrate.js](../src/input/autocalibrate.js))를 쓴다.

**재시도 규칙.** 가장 보수적인 스폰 120ms에서도 예측이 어긋난 크기만 "실패"로 기록하고, 그 크기는 자동으로
다시 시도하지 않는다 — 매번 재시도하면 언젠가 운 좋게 통과한 불안정한 프로필이 저장될 수 있기 때문이다.
높은 스택, 읽을 수 없는 프레임, 캡처 지연, 중단은 그 크기의 성능과 무관하므로 "판정 불가"로 남기고 다음
실행 때 다시 시도한다. 실패로 기록된 크기도 수동 보정으로는 언제든 다시 잴 수 있다.

**실측.** 프로필이 없던 1295×997에서 TURBO로 시작하자 약 2분 반(604피스) 동안 자동 보정해 스폰 120·95·80·65ms와
회전·첫 이동 동시 입력을 모두 통과했고(벽 홀드만 탈락), **스폰 65ms + 동시 입력**으로 저장한 뒤 이어서
200피스를 실효 5.51 PPS로 플레이했다. 폴백·의심 피스·오배치 모두 0회. [실행 로그](turbo-autocal-2026-09-24.txt).

1295×997은 봇이 `window.resizeTo`로 만들 수 있는 크기다. 이 화면에서는 창의 바깥 높이가 작업 영역(작업 표시줄
위, 1032px)을 넘지 못하므로, 1295×999와 1278×1002처럼 작업 영역을 넘는 크기는 앱이 저장된 창을 복원할 때만
나타나고 코드로는 재현할 수 없다.

| 창 크기 | 프로필 |
|---|---|
| 1278×1002 | 스폰 65ms + 동시 입력 |
| 1295×997 | 스폰 65ms + 동시 입력 (자동 보정) |
| 1295×999 | 스폰 120ms + 동시 입력 |
| 1920×1010 (최대화) | 없음. 자동 보정 이전의 실패 기록이 "진행 중" 표시로 남아 있어, 최대화 상태로 켜면 한 번 자동 보정을 시도한다. 120ms에서도 어긋나면 실패로 기록되고 이후 바로 RAPID로 진행한다. |

**한계:** 자동 보정은 프로필이 **없는** 크기에서만 돈다. 키 설정·DAS/ARR·게임 버전이 바뀌면 기존 프로필이
그대로 남아 맞지 않게 되지만 이를 감지하지 못하므로, 수동 보정으로 다시 재거나 `probe/turbo-calibration-*.json`을
지워 자동 보정이 다시 돌게 해야 한다.

## 2026-09-23 재검증 (1,000피스)

**1,000피스 / 208초 완주, 실효 5.03 PPS.** 의심 피스·강제 재동기화·오배치·RAPID 폴백 모두 0회.
[실행 로그](turbo-run-1000-2026-09-23.txt).

측정은 `node src/run.js --mode turbo --pieces 1000`이며, 수치는 TURBO가 보고하는 `turboStats.effectivePps`다.
**`probe/validate_turbo.js`의 `acceptance()` 판정을 거친 기록은 아니다** — 합격 조건의 각 항목(500피스 이상,
의심 피스 제외 PPS ≥5, 의심 피스 ≤3%, 재동기화 ≤1%, 입력 오류·폴백 0)을 모두 충족하지만, 공식 합격으로
쓰려면 그 스크립트로 다시 받아야 한다.

실효 PPS는 구간 내내 4.93 → 5.03으로 단조 상승했고 한 번도 떨어지지 않았다. 검증 지연은 33~49ms로
400ms 제한의 1/10 수준이었다. 609피스에서 캡처 제한을 넘겨 폴백했던 이전 1,000피스 시도와 대비된다.

**보정은 환경마다 다시 떠야 한다.** 뷰포트 1295×999에서는 스폰 95ms가 42번째 피스에서 탈락해
**스폰 120ms + 회전·첫 이동 동시 입력**으로 저장됐다. 2026-09-21 합격 프로필(스폰 65ms)보다 보수적인데도
실효 PPS는 5.323 → 5.03으로 큰 차이가 없다. 보정이 안전한 쪽으로 수렴해도 예측 실행이 손실을 흡수한다.
창 크기가 바뀌면 보정이 무효가 되어 즉시 RAPID로 폴백하므로(`TURBO viewport changed`), 앱 재시작으로
창 크기가 달라진 뒤에는 보정을 다시 떠야 했다 — 다음 날 창 크기별 프로필 저장으로 해결했다(위 2026-09-24 기록).

**함께 확인된 회귀 수정:** 같은 날 RAPID도 1,000피스를 리싱크 0·오배치 0으로 완주했다(400라인, 4.00 PPS).
직전까지 RAPID는 오배치 60%를 내고 있었고, 원인은 추적된 피스 정체성을 필드 위쪽 스폰 영역 판독으로
덮어쓴 것이었다 — 그 영역은 피스를 필드 경계에서 잘라내고 성운 배경이 비쳐, 실제 프레임에서 J를 L로,
축소 캡처에서 J를 I로 오인했다. 스폰 판독은 정체성이 없을 때의 부트스트랩 전용으로 제한했다.

**한계:** 이 구간에도 레벨 전환이 없었다(스테이지업 0). 전환 처리는 여전히 더 긴 런으로 확인해야 한다.

## 핵심 구현

- **예측·검증:** 최대 2피스 계획, 별도 캡처 연결, 검증 완료 전 후속 입력 차단. NEXT 공백은 건너뛰지 않는다.
- **입력:** 실측 보정에 통과한 기능만 사용한다. 타이머 지연 시 키 펄스를 압축하지 않는다. 프로필은 창 크기(뷰포트)마다 따로 측정·저장하고(`probe/turbo-calibration-<w>x<h>@<dpr>.json`) 실행 중인 크기의 것을 쓰며, 프로필이 없는 크기는 TURBO가 시작할 때 자동으로 보정한다. 회전·첫 이동 동시 입력은 측정한 모든 창 모드 크기에서 통과했고, 스폰 지연은 측정마다 65ms / 120ms로 달랐다.
- **화면·복구:** 화면 효과를 임시 고정하고 원래 설정을 복원한다. 레벨 전환 문구와 숨겨진 생성 영역을 읽으며, 재동기화는 전체 상태가 세 번 연속 일치해야 재개한다.
- **안전 제한:** 400ms 검증 제한, 지속 불일치·입력 오류 시 재동기화 또는 RAPID 폴백. 스폰 전 DAS 충전은 비활성화다.

코드는 [예측 루프](../src/turbo.js), [입력 모듈](../src/input/), [비전](../src/vision/vision.js)에 있다.
**Jev는 미도입:** 로컬 개선으로 목표를 달성했고 추가 효과를 입증하지 못했다. Jev의 현재 API·실성능을 별도로 검증한 것은 아니다.
