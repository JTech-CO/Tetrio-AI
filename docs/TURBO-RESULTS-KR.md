## 목표 달성에 필요한 추가 수정

1. 실제 게임 설정에서 보드 바운스와 화면 흔들림이 100%였다. TURBO 동안 두 값을 0으로,
   액션 텍스트를 OFF로 설정하고 종료·오류·모드 전환 시 원래 값으로 복원한다.
   `src/runtime/turbo-environment.js`가 기존 설정 UI를 통해 적용하며, 게임 내부 보드/큐 상태에는 접근하지 않는다.
2. 시각 효과를 고정한 뒤 스폰 65ms와 회전·첫 이동 동시 입력이 120피스 보정에 통과했다.
   불일치·재검사 프레임 0회, 실제 동시 입력 35회, 총 23.474초였다.
3. 매 80피스마다 테두리를 재탐지하고 현재 피스 정체성을 버리던 경로를 수정했다. 창 크기가 같고
   픽셀 검증이 맞으면 기존 기하와 피스 정체성을 유지하고 NEXT만 보충한다. 최초 시각 프로필 적용
   후에는 한 번 새로 보정한다. 정기 검사와 기존 오류/지연 폴백 기준은 제거하지 않았다.
4. `--turbo-only` 검증과 선택형 불일치 진단 파일을 추가했다. 속도에는 초기 피스 식별·상태 검증·복구·
   키 해제를 포함한다. 앱 연결·사전 설정·초기 필드 보정과 준비용 BASIC 60피스는 측정 시작 전에 끝나며
   측정 피스 카운터와 구간 시간에 포함되지 않는다. 측정 중의 재보정과 레벨 전환 대기는 포함한다.
5. 첫 장기 주행은 636피스에서 `LEVEL COMPLETE`의 필드 회전에 걸려 638피스에서 폴백했다.
   저장한 실제 화면으로 원인을 확인하고, 중앙과 필드 밖에 걸친 노란 문구를 검출하는 별도 경로를
   추가했다. 감지 후 입력을 중단하고 두 번 연속 일치하는 전체 상태를 확인한 뒤 재개한다.
   이 구간의 의심 피스는 속도 계산에서 제외하고, 전환 대기 시간은 포함해 보수적으로 합격 여부를 판정한다.

## 구현

- `src/state.js`: 보드·현재 피스·HOLD·NEXT·시퀀스의 순수 상태 전이. 빈 HOLD는 NEXT 2개,
  교환 HOLD는 1개를 소비한다. 읽기 실패한 프리뷰 뒤의 피스를 앞으로 당기지 않는다.
- `src/input/`: 시간 계획 컴파일러, 단조 시계 실행기, 보정 파일 검증. 이벤트 응답을 겹치되
  같은 CDP 소켓의 전송 순서를 유지한다. 타이머가 늦어지면 펄스 간격을 늘리고 압축하지 않는다.
  오류·취소·정상 종료 때 모든 입력 키를 해제하며 해제 실패도 숨기지 않는다.
- `src/turbo.js`: 최대 2피스 예측, 별도 캡처 연결, NEXT 보충, 시퀀스 확인, 재동기화와 RAPID 폴백.
  캡처가 후속 드롭을 가로질러 어느 보드인지 모호해지지 않도록 다음 입력 시작에 검증 장벽을 둔다.
  스폰 대기는 하드드롭 keydown부터 계산하고, 캡처와 AI 계산은 이 대기 시간에 겹친다.
- `src/ai.js`: 선택한 실제 피스와 예상 입력 시간을 반환한다. TURBO만 시간 비용을 평가에 추가하며
  비용 가중치를 상한 0.02/ms로 제한한다. 기본 BASIC/RAPID 평가 가중치는 바꾸지 않았다.
- `src/bot.js`, `src/run.js`, `src/modes.js`: 기존 루프는 `runLegacy()`로 보존하고 모드 선택과
  피스 경계 전환을 연결했다. `--mode turbo`, `--calibration`, 콘솔 `3`/`T`를 지원한다.
- `probe/turbo_calibrate.js`: 2피스 연속 입력 뒤 실제 픽셀을 비교한다. 통과한 스폰 프로필을
  고르고, 회전·첫 이동 동시 입력과 벽 홀드는 별도 실험을 통과한 경우에만 채택한다.
- `probe/validate_turbo.js`: RAPID/TURBO의 500피스 이상 연속 구간을 측정하고 JSON으로 기록한다.
  5 PPS, 의심 피스 ≤3%, 강제 재동기화 ≤1%, 입력 오류·폴백 없음의 조건을 모두 검사한다.

## 백서에서 보완하거나 미룬 부분

1. NEXT 5개를 읽고 무한히 예측할 수 없으므로, 최대 4피스마다 또는 알려진 NEXT가 부족하면
   전체 프리뷰를 보충한다. 라인 클리어/HOLD 등 중간 검증은 필드 전용 캡처를 사용한다.
2. CDP 응답에 붙인 시퀀스만으로 실제 프레임 시점을 증명할 수 없다. 후속 입력을 막는 장벽으로
   이 문제를 제거했다. 화면이 빠르게 돌아오면 스폰 대기 안에서 완료되지만 느린 화면은 속도를 제한한다.
3. 라인 클리어 직후 불일치가 250ms 뒤 일치하는 사례를 실제로 관찰했다. 입력 오류와 화면 효과를
   혼동하지 않도록 최대 400ms 안에서 다시 읽는다. 예측 값을 써서 실제 화면을 덮어 맞추지는 않는다.
4. 스폰 선행 DAS 충전, 내부 열의 ARR 이동, 자동 DAS/ARR 수치 역산은 미구현이다. 벽 홀드는 정확한
   목표 배치와 픽셀 결과를 비교하는 후보 시험이며, 전체 DAS/ARR 설정을 알아냈다는 뜻이 아니다.
5. 게임의 키 바인딩·DAS/ARR·버전 변경은 자동 추적하지 않는다. 변경 후 보정 재실행이 필요하다.
   창 크기/DPR 변경은 거부하며 런타임에서도 주기적으로 확인한다.
6. TURBO의 스테이지업은 레벨 완료 영상 특징을 감지한 횟수로 기록한다. 게임 내부 카운터를 읽지 않는다.

## 초기 500피스 실패 기록 (개선 전)

| 구간 | 피스 | 시간 | 실효 PPS | 결과 |
|---|---:|---:|---:|---|
| RAPID 대조군 | 500 | 140.740초 | 3.553 | 예측 불일치 32, 재동기화 0 |
| TURBO 시작 → RAPID 폴백 | 500 | 131.424초 | 3.804 | 합격 기준 미충족 |

TURBO 자체는 173피스까지 실행됐으며 부트스트랩·복구를 포함한 해당 구간 실효 속도는 3.857 PPS였다.
150피스 시점에는 4.179 PPS, 불일치 0회였지만 이후 1개 검증 구간에서 1피스가 의심 상태로 판정됐다.
강제 재동기화 1회 뒤 높이 12 이상을 감지해 RAPID로 전환했고 나머지 327피스는 RAPID가 실행했다.
따라서 500피스 구간의 3.804 PPS를 TURBO 단독 성능으로 표현하면 안 된다.
TURBO 입력 오류 0회, 일시 재검사 프레임 5회, 마지막 검증 지연 348.66ms였다.
키 해제 실패 예외는 없었지만 게임 내부의 고착 키 카운터를 별도로 읽은 것은 아니다.

최종 판정 `passed: false`. 원본 수치는 [실측 JSON](turbo-validation-2026-09-21.json)에 보존했다.
적극적 입력 프로필을 검증 없이 켜거나 폴백을 제거해 속도 기준을 맞추지 않았다.

두 모드는 동일 세션에서 순서대로 실행하지만 보드와 피스열은 다르다. 통제된 동일 입력 A/B가 아니다.
속도는 최초 피스 식별, 검증, 복구 및 폴백 시간을 포함한 실제 구간 시간으로 계산한다.
드문 검증에서는 개별 오배치 개수를 알 수 없어 불일치 구간 전체를 의심 피스로 센다.
최종 합격 구간과 초기 실패 구간의 JSON은 서로 다른 파일로 보존했다.

## Jev 도입 판단

**미도입 유지.** 로컬 실행 시간과 픽셀 검증을 개선해 이미 목표를 넘었다. 외부 정책 선택기가
속도나 안정성을 더 개선한다는 근거가 없으므로 목표 달성에 불필요한 의존성을 추가하지 않는다.
백서의 로컬 500피스 선행 합격 조건은 이제 충족했다.

백서의 약 178ms 지연 수치는 백서에 인용된 값이며 이번 작업에서 재측정하지 않았다.
백서가 지정한 Jev 커밋의 성능 문서와 모델 계약 원문은 웹 조회에서 가져오지 못했다.
따라서 현재 API와 실성능을 확인했다고 주장하지 않는다. 이 수치가 달라져도 매 피스 입력 경로에
Jev를 넣지 않는다는 판단은 유지된다.

향후 필요성이 입증되더라도 Jev는 20피스 단위 비동기 감독자로만 고려한다. `SAFE`/`BALANCED`/
`SPEED`/`RESYNC`의 고정 정책 외 임의 키·좌표·코드는 허용하지 않고, 켬/끔 구간의 PPS 저하가
없음을 별도로 확인해야 한다. 이번 변경에는 Jev 클라이언트, 외부 API 호출, 새 의존성을 추가하지 않았다.

## 일반 코드 디버깅 후 추가 발견

추가 500피스 재검증은 456피스에서 레벨 전환 문구 검출에 실패해 폴백했고, 회전 중 재보정이 열화로 판정되어 중단됐다. 이 실패도 [원본 JSON](turbo-validation-500-transition-failure-2026-09-21.json)에 보존한다.
실제 화면의 문구가 옅은 노란색(채도 약 0.45)으로 변해 기존 채도 하한 0.7을 통과하지 못했다.
필드 밖으로 걸친 문구의 폭·높이·픽셀 수 조건은 유지하고 채도 하한을 0.35로 조정했다.
실패 화면의 해당 영역을 회귀 테스트 이미지로 추가했고, 기존 정상 화면·노란 O 피스 오검출 방지 테스트와 함께 통과했다.
검출된 전환은 기존의 연속 두 관측 안정화 경로로 처리하며, 합격 기준이나 폴백 제한은 완화하지 않았다.

이어진 준비 주행 없는 1,000피스 시도는 첫 TURBO 입력 전에 높은 스택을 감지해 RAPID로 폴백했다. 이후 일반 모드 실행을 조기에 중단하고 키와 원래 비디오 설정을 복원했다. 이 시도는 합격 실적으로 세지 않는다. 검증 도구도 앞으로 폴백 후 첫 완료 입력 경계에서 종료하도록 개선했다.

다음 1,000피스 재검증도 600피스까지 정상 진행 후, 레벨 전환의 단일 프레임 재부트스트랩에서 HOLD를 null로 오인해 647피스에서 폴백했다. [실패 JSON](turbo-validation-1000-resync-failure-2026-09-21.json)의 648피스에는 종료 경계를 위한 RAPID 1피스가 포함되며 합격이 아니다.
최종 코드는 검증 제한 시간 뒤에 나타나는 전환까지 다루기 위해 일반 불일치 재동기화에도 전체 상태 안정화 검사를 적용한다. 현재 피스·보드·HOLD·NEXT가 세 번 연속 일치해야 재개한다. 단일 프레임에서만 HOLD가 사라지는 상황을 회귀 테스트로 추가했다.

안정화 수정 후 주행은 불일치 1회에서 정상 재개했고 600피스까지 약 5.36 PPS를 유지했지만, 609피스에서 캡처가 400ms 제한을 넘겨 폴백했다. [실패 JSON](turbo-validation-1000-capture-timeout-2026-09-21.json)에 보존한다. 안전 제한은 유지했다. 앞선 1,000피스 합격 기록이 매 실행의 장기 완주를 보장하지 않으며, 현재 환경의 간헐적 캡처 지연은 남은 한계다.

후속 500피스 시도는 335피스 레벨 전환 후 안정화 대기가 끝나지 않아 폴백했다. [원본](turbo-validation-500-stability-timeout-2026-09-21.json)을 보존한다. ZEN에서 새 피스가 보이는 20행 위에 머무는 동안 현재 피스를 식별하지 못하는 원인을 확인했다. 최종 구현은 캡처의 위쪽을 2.5행까지 확장하고 숨겨진 생성 영역의 모양을 픽셀로 읽는다. 실제 J 피스 화면과 빈 영역을 회귀 테스트에 추가했다. 이 경로는 BASIC/RAPID 초기 식별에도 적용한다.
